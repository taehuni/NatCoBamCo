# LastShelter 구현 단계

작성일: 2026-09-11

이 문서는 구현 순서와 단계별 완료 기준을 정리한 초안이다. 사용자와 각 단계를 구체화한 뒤 구현한다. 문서 작성 자체는 기능 구현 완료를 뜻하지 않는다.

## 기준과 현재 상태

- 빌드용 씬은 `00_Intro`, `01_Main`, `02_Collection`이다. 이는 사용자 지정 사항이다.
- 현재 작업 폴더의 저장된 파일을 기준으로 작성했다. Unity 메모리의 미저장 상태와 실행 결과는 검증하지 않았다.
- 현재 Main의 목적지는 Collection, Collection의 목적지는 Main이다. 이전 점검에서 발견한 Collection → tie0 연결은 수정되어 있다.
- 빌드 설정에는 Intro가 없고 테스트 씬들이 포함되어 있다. Collection의 현재 GUID와 빌드 설정의 GUID도 다르다.
- 씬과 폰트에 기존 로컬 변경이 있다. 이후 구현 시 보존한다.
- 테스트 씬은 개발 참고용으로 남기고 빌드 대상에서 제외하는 방향을 제안한다.
- 기존 기능을 활용한다. 씬 복제나 전면적인 시스템 교체는 이번 계획의 전제가 아니다.

## 전체 순서

| 단계 | 목표 | 핵심 작업 | 완료 시 플레이 결과 |
|---|---|---|---|
| 1 | 실행과 씬 왕복 | Intro 시작/종료, 빌드 목록, 스폰, 플레이어·카메라·UI 수명, 상호작용 참조 | Intro에서 시작해 Main과 Collection을 왕복할 수 있다 |
| 2 | 탐사와 자원 | 인벤토리 연결, 자원 획득/지출 API, 실제 채집 노드, 수량 표시, 자원 종류 정리 | 채집한 자원이 귀환 후에도 남고 화면에 표시된다 |
| 3 | 건설과 거점 유지 | 건설 카드 연결, 비용 검증/차감, 배치·회전·철거, 미리보기 비전투화, 건물 상태 복원 | 자원을 써서 지은 시설과 체력이 씬 왕복 후 유지된다 |
| 4 | 실제 전투 | 적 프리팹 갱신, 플레이어 피격, 타워·벽·코어 공격, NavMesh/충돌 설정 | 적이 이동·공격하고 플레이어와 시설이 피해를 주고받는다 |
| 5 | 하루 진행과 결과 | 낮/밤 전환, 귀환 규칙, 웨이브 통합 관리·초기화, 패배·다시 시작 | 채집→건설→방어→다음 날을 반복하고 패배 후 새로 시작할 수 있다 |
| 6 | 생존자와 연구 | 구출·배치·씬 왕복, 정비공 수리, 채집가 보너스, 연구 시간·비용·효과 | 생존자를 구하고 연구하면 다음 탐사·방어에 실제 이득이 생긴다 |
| 7 | 플레이 화면과 운영 | HUD 전체 연결, 메뉴 입력/커서 처리, 일시정지·설정·타이틀 복귀, 저장 범위 결정 | 표시와 실제 규칙이 일치하고 플레이를 중단·재개할 수 있다 |
| 8 | 콘텐츠와 빌드 검증 | 필드 배치·난이도·수치, 피격/채집/건설 피드백, 선택한 플랫폼에서 빌드·반복 검증 | 에디터 밖에서도 의도한 게임 흐름이 재현된다 |

5단계 완료를 첫 번째 플레이 가능한 최소 버전의 기준으로 삼는다. 각 단계에 필요한 최소 UI는 해당 단계에서 연결하고, 7단계에서 전체 화면과 메뉴를 정리한다. 파일 저장은 씬 왕복 중 메모리에 상태를 유지하는 것과 별개의 기능이다.

## 1단계 상세: 실행과 씬 왕복

### 목표

`Intro → 새 게임 → Main → 포털 → Collection → 포털 → Main`을 반복해도 플레이어 조작과 상호작용이 유지되도록 한다.

### 화면과 조작 제안

- Intro에는 우선 게임 제목, `새 게임`, `종료`를 둔다.
- 새 게임은 Main으로 진입한다. 로딩 중에는 시작 버튼을 다시 누를 수 없게 한다.
- 종료 버튼은 빌드에서 애플리케이션을 종료한다. 에디터 검증에서는 에디터 자체를 종료하지 않는다.
- 포털은 기존 E키 상호작용을 유지한다.
- 포털 범위 안에서는 목적지 안내를 보여 주고, 벗어나면 해당 안내를 해제한다.
- 씬 이동 중 포털 입력을 중복 처리하지 않는다.
- Intro에서는 커서를 표시하고, 플레이 중에는 기존 카메라 조작에 맞춰 잠근다.
- 이어하기·설정의 완성 화면은 7단계 범위로 둔다.

### 작업 순서

| 순서 | 작업 | 구체적인 변경·확인 대상 |
|---|---|---|
| 1-1 | 씬 등록 정리 | 실제 빌드 목록을 Intro, Main, Collection 순서로 구성. 현재 SceneAsset 기준으로 GUID를 일치시킴. 활성 Build Profile이 별도 씬 목록을 쓰는지도 확인 |
| 1-2 | 씬 이동 경로 정리 | 이미 수정된 Main↔Collection 목적지를 유지. 코드·버튼 이벤트에 남은 테스트 씬 경로 검사. 씬 이름을 여러 곳에서 제각각 관리하지 않도록 정리 |
| 1-3 | 플레이어 수명 확인 | Main의 플레이어·카메라·무기·필수 UI가 함께 유지되는지 확인. Main 재진입 시 새 씬의 중복 플레이어를 제거하고 남아 있는 객체로 참조 연결 |
| 1-4 | 스폰 지점 정리 | Main과 Collection마다 활성 SceneSpawnPoint를 하나씩 유지. 위치·회전·바닥 충돌 확인. 시작 시점과 재진입 시점 모두 의도한 지점에 배치 |
| 1-5 | 상호작용 UI 복구 | Main의 잘못된 PlayerInteractUI 스크립트 참조 복구. 버튼·텍스트·슬라이더 할당. 서로 다른 상호작용 대상이 안내를 덮어쓰거나 지우는 문제 점검 |
| 1-6 | Intro 진입점 구현 | 새 게임 시작과 종료를 연결. 새 세션 초기화의 진입점을 마련하고 중복 실행 방지. 이후 단계의 자원·건설·생존자 상태도 이 진입점에 초기화를 연결 |
| 1-7 | 왕복 검증 | 실제 Intro에서 시작해 Main→Collection→Main을 3회 반복. 카메라·입력·UI·이벤트 중복 및 오류 확인 |

기존 Main의 플레이어·카메라 구조와 PlayerScenePersistence를 우선 활용한다. 세션 시작과 종료를 관리하는 작은 진입점을 두되, 현재 모든 매니저를 하나의 거대한 클래스로 합치지 않는다. 기존 싱글턴들이 같은 오브젝트를 중복 제거 대상으로 처리하지 않도록 각 객체의 수명을 확인한다.

### 완료 기준

- [x] 빌드 목록의 첫 씬이 Intro이며 포함된 게임 씬은 지정된 세 씬이다. (배포 빌드는 아직 실행하지 않음)
- [x] 게임 시작 버튼으로 Main에 한 번만 진입한다. (Unity Play에서 버튼 이벤트 중복 호출 검증)
- [ ] 플레이어가 지정된 스폰 위치에 배치되고 이동·카메라 조작이 된다.
- [ ] 포털 안내와 E키 이동이 양방향으로 작동한다.
- [x] 왕복 3회 후 활성 플레이어·게임 카메라·EventSystem에 중복이 없다. (Unity Play에서 포털 로드 메서드를 호출해 검사)
- [ ] Main 재진입 후에도 나침반·상호작용 UI 등 기존 플레이어를 참조하는 UI가 올바른 대상을 사용한다.
- [ ] Missing Script, 씬 로드 실패, 파괴된 객체 참조 오류가 없다.
- [x] Intro와 플레이 화면에서 커서 상태가 맞고 전환 도중 중복 시작 호출이 발생하지 않는다. (직접 키보드·마우스 조작 검증은 별도)

이번 단계의 통과는 자원 저장·전투·하루 진행의 완료를 뜻하지 않는다. 해당 기능은 아래 단계의 기준으로 별도 검증한다.

## 2~8단계에서 구체화할 내용

### 2. 탐사와 자원

- ResourceInventory를 실제 플레이 흐름에 연결한다.
- 현재 Wood/Metal/Food와 UI에 있는 부품 비용의 불일치를 해소한다. 자원 종류는 구현 전에 결정한다.
- 잔액 확인과 여러 자원의 일괄 차감 API를 만든다. 일부 자원만 차감된 뒤 실패하지 않도록 한다.
- Collection에 선택한 자원 종류를 실제로 배치하고 수량을 표시한다.
- 채집한 노드는 재진입 시 중복 획득되지 않도록 유지한다. 하루마다 재생할지 영구 소진할지는 결정 사항이다.
- 완료 기준: 채집→귀환 후 수량 유지, 부족한 자원 지출 거절, 충분한 자원 지출 시 정확한 차감.

### 3. 건설과 거점 유지

- 실제 구현된 건물부터 건설 카드와 프리팹을 일치시킨다. 설명만 있는 건물은 목록에서 구분하거나 제외한다.
- 미리보기는 공격·수리·피격 대상으로 작동하지 않게 한다.
- 배치 가능 여부, 비용 충족, 생성 성공을 하나의 건설 처리로 연결한다.
- 철거 레이어를 복구하고 철거 환급 정책을 정한다.
- 시설 종류·위치·회전·체력 등 거점 상태를 세션 데이터에 보관한다. 중복 생성 없이 Main 재진입 시 복원한다.
- 완료 기준: 시설을 건설하고 일부 손상시킨 뒤 씬을 왕복해도 같은 상태로 남으며 비용이 한 번만 차감됨.

### 4. 실제 전투

- Main 스포너의 Enemy.prefab을 현재 분리된 적 모듈 구조에 맞춘다. 이동·체력·공격 수치와 행동 컴포넌트를 검증한다.
- 플레이어에게 피해받기·체력 0 상태를 구현하고 적 공격과 연결한다. 결과 화면 전환은 5단계에서 연결한다.
- 일반·원거리·고속·탱크 중 첫 버전에 사용할 적을 정해 각각 역할대로 작동하게 한다.
- 배치한 벽/타워와 적의 NavMesh, 공격 지점, 장애물 판정을 함께 검증한다.
- 완료 기준: 적 이동→시설/플레이어 공격→체력 감소→적/시설 파괴가 실제 플레이에서 성립함.

### 5. 하루 진행과 결과

- GameManager를 낮·밤의 공통 기준으로 삼아 조명과 생존자/HUD 연동 지점을 마련한다.
- 낮의 종료 조건, 필드에 남아 있을 때의 처리, 밤에 포털을 사용할 수 있는지 결정한다.
- 여러 스포너를 하나의 방어 진행으로 집계한다. 모든 생성 완료와 생존 적 수를 기준으로 방어 종료를 판정한다.
- 다음 날 웨이브 상태를 초기화하고 날짜별 난이도 데이터를 적용한다.
- 코어/플레이어 체력 0 시 게임 진행을 종료하고 최소 결과·다시 시작 화면을 연결한다.
- 새 게임에서 날짜·자원·건설·채집 기록 등을 초기화한다. 정상 씬 왕복과 새 게임 초기화를 구분한다.
- 완료 기준: 최소 이틀 연속 진행, 패배 후 재시작, 필드에서 밤 전환 등 경계 상황 통과.

### 6. 생존자와 연구

- Collection에 구출 대상과 필요한 경비 적을 배치하고 SurvivorManager를 연결한다.
- 구출한 생존자의 Main 배치, 이후 씬 왕복, 파괴된 homePoint 재연결을 처리한다.
- 정비공 수리와 채집가 보너스를 연결하고 식량/부상 규칙의 범위를 정한다.
- 연구에 비용·진행 시간·완료 효과·레벨 상한을 연결한다. 연구원 보너스는 실제 연구 시간 계산에 반영한다.
- 완료 기준: 구출 전후의 수리·채집·연구 효과 차이를 확인하고, 재진입해도 구출이나 연구 효과가 중복되지 않음.

### 7. 플레이 화면과 운영

- 날짜·페이즈·남은 시간·웨이브·자원·플레이어/코어 체력을 실제 데이터와 연결한다.
- 탄약·재장전·스태미나는 사용할 규칙을 결정한 뒤 구현하거나 관련 표시를 정리한다.
- 메뉴가 열렸을 때 이동·사격·카메라 입력과 커서 상태를 일관되게 제어한다.
- 일시정지·설정·타이틀 복귀를 연결한다.
- 저장/불러오기가 필요한지, 필요하다면 저장 시점과 복원 대상을 정해 구현한다. 이어하기는 저장 기능 완료 후 노출한다.
- 완료 기준: 화면 수치와 실제 상태 일치, 메뉴 전환 후 입력/시간 정상 복구, 채택한 저장 기능의 재실행 검증.

### 8. 콘텐츠와 빌드 검증

- 정해진 자원·시설·적 구성을 기준으로 배치와 수치를 조정한다. 테스트용 체력·방어 값은 실제 밸런스로 교체한다.
- 채집·건설·발사·피격·파괴에 필요한 최소 시각/소리 피드백을 연결한다.
- 목표 플랫폼을 확인하고 실제 빌드에서 새 게임·왕복·방어·패배·재시작을 검증한다.
- 승리 조건을 채택했다면 그 종료 경로도 확인한다.
- 완료 기준: 새 실행에서 의도한 게임 흐름을 재현하고 치명적인 참조·진행 오류가 없음.

## 결정 사항은 해당 단계에서 좁힌다

현재 확정된 것은 빌드용 세 씬이다. 다음은 구현 순서에 맞춰 구체화할 게임 규칙이며 아직 확정된 기획이 아니다.

| 구체화 시점 | 결정할 내용 |
|---|---|
| 1단계 | Intro 최소 구성과 새 게임 시작 흐름 |
| 2단계 | 자원 종류, 채집 노드 재생 규칙 |
| 3단계 | 첫 건설 목록, 비용, 철거 환급 |
| 4단계 | 사용할 적 종류, 플레이어 피격·사망 규칙 |
| 5단계 | 낮 종료/귀환, 밤 포털, 방어 종료, 최종 승리 유무 |
| 6단계 | 생존자 식량·부상·성장, 연구 목록과 효과 |
| 7단계 | 탄약·스태미나·저장 기능의 채택 범위 |
| 8단계 이전 | 목표 빌드 플랫폼과 배포 범위 |
