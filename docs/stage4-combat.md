# 4단계 전투 연결 점검

## 작업 범위

- 플레이어 피격 처리는 강철님 담당으로 남겨 둔다.
- 이번 작업은 Main에서 스폰된 적이 움직이지 않는 문제를 해결한다. 기존 적 AI 스크립트와 팀원 테스트 씬은 변경하지 않는다.

## Main 적 이동 문제 (2026-09-14)

- Main 스포너 4개는 모듈 분리 전 데이터가 남은 `Enemy.prefab`을 사용했다. 체력·이동·공격 수치가 옛 EnemyAI 항목에만 있고, 기지 공격 행동 컴포넌트도 없었다.
- 수정 전 Play 측정: 4곳 모두 NavMeshAgent는 NavMesh에 올라갔으나 실제 속도 0, 체력 0, EnemyBaseAttackBehaviour 없음, 이동 경로 없음이었다. 5초 동안 수평 이동이 없고 바닥에 맞추는 높이 보정만 발생했다.
- `MainEnemy.prefab`을 별도로 만들고 Main 스포너 4개에 연결한다. 기존 Enemy.prefab은 jim01/tie0 테스트 씬에서도 사용하므로 보존한다.
- 기존 수치를 각 모듈에 반영: 체력 30, 이동 속도 3.5, 공격 거리 1.5, 공격력 10, 공격 간격 1.5초, 마비 최대 누적 100 및 방어 1.
- 기존 EnemyBaseAttackBehaviour와 BuildingAttackSlotManager를 연결하고 PlayerWall/PlayerTower 등 프로젝트 레이어를 지정한다. 탐지/이탈 거리는 기존 RangeEnemy 설정과 같은 8/12를 사용한다.
- NavMesh 재생성, 스폰 위치 변경, 적 스크립트 수정은 하지 않는다.

## 검증

- 실제 Main 스포너 4개의 기존 SpawnEnemy 함수를 호출한 뒤 정상 AI/행동/NavMeshAgent 갱신으로 5초간 이동을 측정했다. 강제 Warp나 SetDestination은 사용하지 않았다.
- 수정 후 4곳 모두 약 13.46~16.01m 이동했고 속도 3.5, 체력 30, 기지 공격 행동이 적용됐다. 검사 중 Error/Exception은 0개였다.
- 전체 웨이브, 모든 건물 공격/파괴, 플레이어 피격은 이번 검증 범위가 아니다.
- 로컬 임시 결과: `MainEnemyMovement-before.json`, `MainEnemyMovement-after.json`.

## 코어·벽·타워 전투 확인 (2026-09-14)

- 코어 공격 실패를 재현했다. 적은 코어 표면에서 약 2.20 떨어진 목적지에 도착했지만 공격 거리는 1.5여서 체력이 100에서 줄지 않았다.
- `MainEnemy.prefab`의 NavMeshAgent 정지 거리를 1에서 0.1로, EnemyBaseAttackBehaviour의 목표점 추가 거리를 1에서 0으로 조정했다. 공격 거리·공격력·속도와 기존 팀원 스크립트는 변경하지 않았다.
- 수정 후 Main의 스포너 4곳에서 생성한 적 모두 정상 AI로 접근해 각각 코어를 공격했다. 표면과의 거리는 약 1.20~1.37이었고 코어 체력은 100에서 80으로 감소했다. 별도의 단일 적 검사에서도 100에서 95로 감소했다(공격력 10, 코어 방어력 5).
- 기관총 타워의 기존 공격으로 적 체력이 30 → 20 → 10으로 감소하고 적 오브젝트가 제거됐다. 타워는 생존했다.
- 기존 벽 프리팹 12개를 Play 중 코어 주변에 닫힌 형태로 배치해 경로를 차단했다. 일반 적이 벽을 타깃으로 선택하고 7 피해를 줬으며 코어 체력은 유지됐다. 변경 후 설정에서도 다시 통과했다.
- 벽의 기존 체력 99,999는 유지했다. 벽 파괴까지 기다리는 검사, 열린 경로에서의 우회 검사, 다른 타워 종류, 전체 웨이브·패배·재시작, 플레이어 피격은 이번 통과 범위가 아니다.
- 검사는 Main의 기존 SpawnEnemy 함수와 실제 프리팹을 사용한 프로그램 실행이다. 코어·벽에 피해 함수를 직접 호출하거나 적에게 목표를 강제 지정하지 않았다. 테스트 건물·적은 제거하고 코어 체력은 검사 전 값으로 복원했다. 검사 중 Error/Exception은 없었다.
- 로컬 임시 결과: `MainCombatChecks-before-core-fix.json`, `MainCombatChecks-result.json`, `MainCoreDirectionsCheck-result.json`, `MainWallCombatCheck-result.json`.

## 다수 적의 대기·경로 재개 확인 (2026-09-14)

- Main Play에서 밤 단계로 전환하고 기존 스포너 4개의 정상 갱신으로 첫 웨이브 20마리(각 5마리, 생성 간격 3초)를 생성했다. 20마리 모두 NavMesh에 올라갔으며, 관찰 시점에 15마리가 코어를 공격하고 5마리가 뒤에서 대기했다.
- 앞의 적 15마리를 기존 TakeDamage 함수로 처치한 뒤 대기하던 5마리 모두 새로 코어 공격을 시작했다. 이번 조건에서는 앞의 적 때문에 잠시 기다리는 상태가 영구적인 멈춤으로 이어지지 않았다.
- 기존 벽 프리팹 12개로 코어 주변 경로를 닫고 스포너의 SpawnEnemy 함수로 8마리를 생성했다. 그중 4마리의 벽 공격과 벽 3개의 체력 감소를 확인했다.
- 기존 BuildingSystem.TryRemoveBuilding으로 벽을 철거한 후 8마리 모두 정상 AI로 코어에 도달해 공격을 재개했다. 검사 중 Error/Exception은 0개였다.
- 긴 관찰을 위해 Play 중에만 코어 최대/현재 체력을 10,000으로 올렸으며, 종료 시 원래 값으로 복원하고 테스트 적·벽을 제거했다. Play도 종료해 웨이브 상태를 초기화했다. 이번 검사로 게임 스크립트·프리팹·씬 설정을 추가 변경하지 않았다.
- 적 처치는 테스트 코드의 피해 호출이며 플레이어 무기 조작 검사가 아니다. 철거는 기존 함수를 실행한 것으로 X키·마우스 선택 입력은 이번에 검사하지 않았다. 첫 웨이브와 지정한 폐쇄 벽 배치에서의 결과이며, 전체 5웨이브·날짜 전환·모든 배치의 군중 이동까지 검증한 것은 아니다.
- 로컬 임시 결과: `MainCrowdChecks-result.json`.

## 전체 웨이브·날짜 전환 확인 (2026-09-15)

- 기존 Main 스포너 4개, 각 5웨이브·웨이브당 5마리·생성 간격 3초를 유지해 총 100마리 생성을 확인했다. 각 웨이브에서 마지막 한 마리가 살아 있는 동안 Day 1/Defense가 유지됐고, 5웨이브의 마지막 적 처치 후 정확히 Day 2/Gathering으로 전환됐다.
- 실제 벽 카드의 StartPlacement/TryBuild로 설치한 벽 1개의 동일 인스턴스·위치·체력과 자원 4종 보유량이 날짜 전환 후 유지됐다. 이 검사는 모든 건물 종류의 재검증은 아니다.
- **재현된 문제: Main에 머문 채 다음 밤을 시작하면 적 생성 없이 Day 3/Gathering으로 넘어간다.** EnemyMaker 4개의 currentWave가 모두 5로 남아 있었고, 새 밤에 CompleteDefense가 다시 호출된다. 현재 코드에는 날짜 변경에 따른 웨이브 상태 초기화가 없다.
- **추가 관찰: 1~4웨이브는 마지막 적이 살아 있어도 다음 웨이브 번호로 넘어간다.** 한 마리(체력 30)를 남기고 1초 후 측정했을 때 모든 스포너 번호가 각각 2/3/4/5였다. EnemyMaker.Update의 `!spawningWave && currentWave < totalWaves` 조건이 CheckWaveClear보다 먼저 다음 웨이브를 시작하므로, 기존의 전멸 확인 및 waveDelay 대기를 우회한다. 전멸 후 다음 웨이브가 의도라면 이 시작 조건도 수정해야 한다.
- 위의 다음 밤 오류를 기록한 뒤 테스트 날짜만 Day 2/Gathering으로 복원해 수집 기능을 독립 검사했다. 전날 채집한 스포너 3곳이 모두 다시 활성화됐고 각 지점의 자원이 전날과 달랐다. 따라서 이 결과는 오류 없이 이어진 전체 2일 플레이의 통과를 의미하지 않는다.
- Day 2에 한 곳을 채집하고 Main/Collection을 왕복했을 때 자원 종류와 채집 여부, 보유 자원이 유지됐다. Main의 테스트 벽은 Collection에서 비활성 상태로 보관되고 Main 복귀 시 같은 인스턴스·위치·체력으로 활성화됐다.
- Collection을 다녀와 새로 생성된 Main 스포너는 Day 2 밤에 모두 Wave 1로 시작하며 첫 적 4마리를 생성했다. 씬 재입장이 위 초기화 문제를 가리는 것을 확인했다. 재입장 후 두 번째 밤의 5웨이브 전체를 반복 검증한 것은 아니다.
- 검사는 실행 중인 Unity에서 수행했다. 적 처치는 기존 TakeDamage 호출, 채집은 CollectComplete 호출, 밤 시작은 SkipGathering 호출, 씬 이동은 LoadSceneAsync로 실행했으며 물리적인 키·마우스 조작 검사가 아니다. 코어 체력 10,000 및 벽 건설에 부족한 자원 지급은 Play 중 테스트에만 사용했다. Play 종료로 테스트 상태를 정리했고 Error/Exception은 0개였다.
- 게임 스크립트·씬·프리팹 수정은 하지 않았다. 다음 수정 후보는 EnemyMaker의 날짜별 상태 초기화와, 전멸 대기가 의도일 경우 웨이브 시작 조건이다.
- 로컬 임시 결과: `MainCycleChecks-result.json`, 초기 웨이브 조기 진행 관찰 `MainCycleChecks-wave-advance.json`.

## 웨이브 초기화·전멸 대기 수정 (2026-09-15)

- 사용자 승인 후 `EnemyMaker.cs` 한 파일을 수정했다. 날짜 변경을 감지하면 웨이브 번호, 해당 웨이브 생성 수, 생성/대기 타이머, 생성/대기 플래그를 초기화한다. Defense 여부를 확인하기 전에 처리하므로 낮 동안에도 다음 밤을 준비한다.
- 즉시 시작 조건을 첫 웨이브에만 적용했다. 이후 웨이브는 기존 CheckWaveClear의 전멸 확인과 waveDelay 대기 경로로 시작한다.
- 기존 공개 설정인 생성 간격, 웨이브 수, 웨이브당 적 수, 웨이브 대기 시간은 유지했다. GameManager, 적 전투 스크립트, 씬·프리팹은 수정하지 않았다.
- 수정 후 Unity에 컴파일된 EnemyMaker가 반영된 것을 확인하고 실제 Play 검사를 통과했다. 첫날 전투 시작부터 둘째 날 전투 종료까지 Main을 재로드하지 않고 같은 스포너 4개로 각 5웨이브·100마리, 총 200마리를 생성했다.
- 10개 웨이브 모두 마지막 적 한 마리를 남긴 동안 웨이브 번호와 날짜가 유지됐다. 마지막 적 처치 후 다음 웨이브까지의 대기는 8번 모두 약 2.04~2.09초였다(기존 waveDelay 2초).
- 각 밤 종료 후 날짜가 정확히 한 번 증가해 Day 1 → Day 2 → Day 3으로 진행됐다. 두 번 모두 스포너 4개의 웨이브 번호·생성 수·타이머가 0, 생성/대기 플래그가 false로 초기화됐다. Main에 머문 채 시작한 둘째 밤도 Wave 1부터 전체 5웨이브를 정상 진행했다.
- 실제 카드로 설치한 벽 1개의 인스턴스·위치·체력과 자원 4종 보유량이 두 날짜 전환 동안 유지됐다. Day 3에 Collection으로 이동하자 Day 1에 채집한 3곳이 모두 새 날짜로 활성화됐고, 한 곳 채집 후 같은 날 왕복해도 종류·채집 여부·보유 자원과 Main 벽이 유지됐다. 날짜를 강제로 복원하지 않은 연속 진행 검사다.
- 기존 SkipDefense로 생성 중인 Day 3 전투를 끝냈을 때 Day 4의 이전 적과 웨이브 상태가 정리됐고, 다음 밤 Wave 1에서 첫 적 4마리가 정상 생성됐다.
- 적 처치·채집·건설·밤 시작은 기존 게임 함수를 테스트 코드에서 호출했다. 물리적인 키·마우스 조작 및 전투 난이도 검사는 아니다. 기존 생성 간격·웨이브 수·적 수를 유지했고, 코어 체력 10,000과 부족한 벽 재료 보충은 Play 중 테스트에만 사용했다. 검사 중 Error/Exception은 0개였으며 Play를 종료해 임시 상태를 정리했다.
- 로컬 임시 검사/결과: `MainCycleFixChecks.cs`, `MainCycleFixChecks-result.json`. 검증 때문에 게임 코드를 추가 수정하지 않았다.
